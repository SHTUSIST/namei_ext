# 近邻系统是怎么论证"值得新加一个机制"的(2026-08-05)

这一轮查了十六个与本项目形态相近的系统,看它们各自怎么回答同一个问题——**overlayfs 已经能叠出视图并提供写隔离,挂载命名空间加绑定挂载已经能让不同进程组在同一路径看到不同东西,块级克隆已经能便宜地复制一棵树,你为什么还要新加一个机制。**

这份文档不是相关工作综述,而是论证方法的调查:哪些辩护站得住、哪些一查文档就塌、哪些会反过来伤到我们自己。文末第七节按"本轮亲手抓原文核实"与"检索环节抓取、本轮未重抓"逐条标注,写进论文之前请按那一节的分类自行处理。

## 一、谁回答了这三个问题中的哪几个

先把三个被否决对象说清楚,后面的表才读得懂。

**overlayfs** 是内核自带的层叠文件系统:挂载时给它一个下层目录和一个上层目录,读的时候先看上层、上层没有再看下层,写的时候一律写到上层去,于是下层内容不被改动。**挂载命名空间加绑定挂载**是另一套东西:内核为一组进程各自保存一份挂载表,"绑定挂载"把一个已有目录再挂到另一条路径上,例如把 `/srv/repo-a` 绑定挂到 `/workspace`,于是不同进程组在同一条路径上看到不同的树。**块级克隆**指文件系统只复制一份指向同一批磁盘数据块的记录、不搬运数据本身,btrfs 的子卷快照和 XFS 的 reflink 都属于这一类,复制一棵大树因此很便宜。

## 二、站得住的辩护(可以学的)

**第一条,TClone 的页缓存双份。** 它不说现成机制慢,而是指出一个换配置、换文件系统都绕不开的事实:页缓存(内核为文件内容维护的内存缓存)按每个文件各自的地址空间建索引,而地址空间挂在文件记录上;快照拿到自己的文件记录,同一份内容就在内存里存两份。**论证形式可以学,内容我们用不上**——我们不复制内容、不给谁分配新的文件记录,这条路对我们是关着的。而且它只对"给快照分配自己文件记录"的那类文件系统成立,对 overlayfs 不成立,因为未被改动的下层文件在多个 overlay 挂载里是同一个文件记录。(TClone 的原句转引自检索环节,我本轮未重抓。)

**第二条,DeltaBox 的层栈缺口——这是本轮对我们最有用、同时也最危险的一条,单独讲透。**

原句我本轮亲手抓了 arXiv 正文第 4.1 节核实:

> `Standard Linux overlayfs fixes its layer stack at mount time; reconfiguring it requires an umount/mount cycle, impossible while the agent holds open files and untenable at the checkpoint rates MCTS demands.`

(标准的 Linux overlayfs 在挂载时就把层栈固定了;要重新配置就得卸载再挂载一次,而在智能体还握着打开的文件时这做不到,在蒙特卡洛树搜索所要求的检查点频率下也撑不住。)

**有用在哪。** 这正是我们想讲的那条缺口,而且已经由同行写进论文当作自己的动机。引用它比我们自己主张风险小得多。它还证明了一件事:**缺口陈述可以只靠一句接口事实成立,未必需要配一条开销曲线。**

**危险在哪,必须写清楚。** DeltaBox 解决这条缺口的办法**不是另造一个机制,而是直接改 overlayfs**。它用的是 XFS 加 reflink 作底,再配一个**改过的 overlayfs 内核模块**,通过一个自定义的 ioctl(ioctl 是让用户态程序向内核下达特定控制命令的接口)在不卸载的情况下重排层栈。

**于是审稿人会问我们一个很尖锐的问题**:既然给 overlayfs 加一个重排层栈的 ioctl 就能做到运行中换视图,为什么要在名字解析路径上另开一个扩展点?

**我们唯一站得住的答复是粒度。** 改层栈是**按挂载**生效的,同一个挂载点上的所有使用者一起换;我们的判定是**按任务**的,同一个挂载点上不同的任务可以同时看到不同的东西。这个差别是真的,但**必须在论文里明写并引用 DeltaBox**,不能等审稿人提出来。

**第三条,Turso 对 git worktree 的强制点论证。** 原句是 `The isolation is purely conventional, not enforced.`(那种隔离纯粹是约定俗成的,不是被强制的。)形状正是我们需要的那一类:不说对方做不到,而是指出对方的隔离靠使用者自觉遵守约定,没有任何机制拦住不遵守的人。缺点是它只是产品问答里的一句话,没有任何测量,只能当体裁先例,不能当论文级证据。(转引,未重抓。)

**第四条,EdenFS 的 root 助手进程。** 原句是 `mounting and unmounting directories requires elevated privileges, and cannot be done by normal users`(挂载和卸载目录需要提升的权限,普通用户做不了),因此 Meta 的生产系统被迫常年跑一个有 root 权限的助手进程。**这是可以点名出处的工业证据**,用来回应"直接用挂载命名空间加绑定挂载就行了"这一问,比我们自己推断有力得多。(转引,未重抓。)

**第五条,EdenFS 的 redirections 用法。** Meta 用绑定挂载覆盖的,是整棵不含任何受版本控制文件的生成物目录,粒度是整个目录,配置是每个检出一份的静态文件。**这说明工业实践里绑定挂载恰好被用在不需要按名字逐个挑选的场合。** 审稿人若拿 Meta 举例反问我们"人家用绑定挂载用得好好的",答案就在他引的同一份文档的下一句里。(转引,未重抓。)

**第六条,微软的"前提被破坏"论证形状。** 它不说现成机制做不到,而是逐条指出那些机制成立所依赖的前提在这个场景里被破坏了。原句是 `The sparse-checkout is static. So if you've configured it to include folder A and someone later adds a dependency on folder B…, your builds will start to break`(稀疏检出是静态的。所以如果你配好了包含目录 A,后来有人加了对目录 B 的依赖,你的构建就会开始失败。)**形状可借,机制不可借**:可借的是"指出对方依赖的前提在本场景不成立"这种写法,不可借的是它具体谈的稀疏检出,那是 git 的功能,和内核无关。(转引,未重抓。)

## 三、不站得住的辩护(不能学的,其中两条会直接伤到我们)

**第一条,YoloFS 的成本论证不成立,而且这一条直接威胁我们。**

它说把基线目录树镜像到上层太贵,原句是 `This design is too expensive for agent workloads.`(这个设计对智能体负载来说太贵了。)但它给的三个子理由里有两个被现成的挂载选项免掉,这两个选项我本轮亲手抓内核官方文档核实过:

- "改个文件名就要整文件复制"被 `metacopy` 免掉。官方原句:`When the "metacopy" feature is enabled, overlayfs will only copy up metadata (as opposed to whole file), when a metadata specific operation like chown/chmod is performed.`,而且 `The data will be copied up later when file is opened for WRITE operation.`
- "改目录名要递归复制整棵子树"被 `redirect_dir` 免掉。官方原句:改名时 `the directory will be copied up (but not the contents). Then the "trusted.overlay.redirect" extended attribute is set to the path of the original location from the root of the overlay.`

真正绕不掉的只剩"在上层补建全部父目录",而那只是建空目录。

**教训写死**:如果我们也去写针对 overlayfs 的成本论证,同一句挂载选项就能当场把它推翻。**所以我们的实验里,overlayfs 那一条件必须开着 `metacopy` 与 `redirect_dir` 跑**,否则等于拿一个被人为削弱的 overlayfs 作对照,得出的数字没有说服力。这一条已经同步补进实验计划的冻结配置一节。

**第二条,YoloFS 拒绝挂载的那句字面是错的。**

它写的是 `Mount-based isolation, such as bind mounts and mount namespaces, is the opposite: it can expose additional paths, but it cannot revoke access to visible paths.`(基于挂载的隔离恰好相反:它能暴露额外的路径,但不能撤销对已可见路径的访问。)

**这句话不成立。** `mount_namespaces(7)` 手册页自己就给了反例,我本轮亲手抓原文核实:命令是 `mount --bind /dev/null /etc/shadow`,随后 `cat /etc/shadow` 没有任何输出,手册的解释是 `The above steps, performed in a more privileged mount namespace, have created a bind mount that obscures the contents of the shadow password file, /etc/shadow.`

**撑得住的是它背后的意思**,但需要换成准确表述:挂载是一次性布置好的静态安排,不是每次访问重新走一遍的判定;而且已经打开的文件描述符撤不掉。**我们只能用后面这个说法,绝不能沿用它的字面表述。**

**第三条,TClone 关于"一个分支不能从另一个分支再分叉"的因果解释说错了。** 它归因于每一层都是挂载点,但内核官方文档有专门一节讲嵌套,我本轮亲手核实的原句是:`It is possible to use a lower directory that is stored on an overlayfs mount. For regular files this does not need any special care.` 它的结论在"父分支还活着并继续写"这个前提下仍然成立,但**因果写错这件事本身就是教训:审稿人只要查一次内核文档就能拆掉。**

**第四条,BranchFS 的逐项打勾表有两格被它自己引的参考文献推翻。** 一格是"联合文件系统没有把改动合并回父层的原生能力"——device-mapper 的 `snapshot-merge` 目标做的正是这件事;另一格是"挂载需要 root 权限"——`userxattr` 挂载选项使得在用户命名空间内以非 root 身份挂 overlayfs 可行。**教训:逐项打勾的对照表是高风险体裁,一格出错整张表都可疑。** 我们自己那张"七件事分别由谁做"的表因此必须每格写具体做法、写清适用条件,不能只打勾叉。(这两条转引自检索环节,我本轮未重抓,写进论文前请自行核。)

**第五条,Ori 只报粒度差、不说换来了什么。** 原句是 `WAFL and ZFS operate at the block layer, whereas Ori works on top of an existing file system at a file granularity.`(WAFL 和 ZFS 工作在块层,而 Ori 工作在一个已有文件系统之上,粒度是文件。)它全程没有指出块层写时复制的任何缺陷,也没有说文件粒度换来了什么。这正是本项目明令禁止的写法——粒度不同不自动等于贡献。它能这么写,是因为它在别处已经用别的硬能力把自己撑住了;我们目前没有那样的余地。(转引,未重抓。)

## 四、会直接伤到我们的三条

**第一条,Turso 自己承认一条命令就能得到相近的隔离。** 原句是 `While you could achieve similar isolation with a bwrap call…, the key difference is persistence and queryability`(虽然你用一条 bwrap 命令就能得到相近的隔离,但关键差别在于持久化与可查询。)bwrap 是 bubblewrap,一个不需要 root 就能建沙箱的命令行工具。**这是"现成工具的一条命令就能得到相近效果"这个风险的最强实证**,而且是这个领域里的产品方自己写的。我们必须预先想好:当审稿人拿一条命令行来问"这不就够了吗",我们要拿出什么。(转引,未重抓。)

**第二条,BranchFS 的独立模式把语义缺口全部实现在用户态守护进程里,一行内核代码都没改。** 这一句掐断了"存在语义缺口,所以必须进内核"这个推论。**我们要论证的不能是"有缺口",必须是"在内核这一层做,比在用户态做多出了什么"。**(转引,未重抓。)

**第三条,微软的转向。** 当有别的系统(构建依赖分析)能替你算出每个任务该看哪些文件时,静态清单加现成机制就够用了,专用的那一层会退化成只适用于极少数场景。这是对我们适用范围的直接压缩,不是对机制正确性的质疑,但在评审里两者的杀伤力相当。(转引,未重抓。)

## 五、在内核里新加扩展点的那几篇,论证结构是什么

先说清楚查了哪几篇以及可信度:Bento(FAST 2021)、ExtFUSE(ATC 2019)、XRP(OSDI 2022)、lwC(OSDI 2016)四篇的 PDF 是检索环节从 USENIX 官网下载后逐行比对的;sched_ext 的内核文档与补丁封面信、Landlock 的内核文档是 curl 取回后逐句核对的。**这一节的具体引文我本轮均未重抓,写进论文前须自行核实。**

提炼出的共同结构,这是我们可以照搬的部分:

1. **先把现在这条路要付的代价按层拆开量出来**,而不是笼统说慢。
2. **指出这笔代价来自设计里固有的东西**,不是实现没调优。
3. **说明为什么在现有层次上修不好**——这一步决定了要不要新加机制。
4. **说明为什么这个能力必须由内核提供**,而不是用户态做不到。
5. **把新加的东西限制到最小**,并说明限制本身如何换来安全性或可验证性。
6. **给出证据**:既有机制的代价、新机制的代价、以及在真实负载上的端到端影响。

**对我们的直接含义**:第 4 步是我们目前最弱的一环,因为 BranchFS 已经证明语义缺口可以在用户态补上。我们能给的答案只能是"每任务粒度、零挂载、可在运行中改"这三条**同时**成立时用户态做不到或代价高得多——而这三条目前一条数据都没有。

## 六、我们该采用哪种论证,不该采用哪种

**应当采用**:能力粒度论证(按任务对比按挂载)加上强制点论证(隔离是靠使用者遵守约定,还是由机制拦住)。理由是这两条不依赖我们拿不出的性能数据,而且 DeltaBox 已经替我们把"按挂载改层栈"这条路的存在证明了,我们只需说清粒度差别。

**不应当采用**:

- 针对 overlayfs 的成本论证——被 `metacopy` 与 `redirect_dir` 推翻。
- 任何形式的"挂载做不到"——被 `mount_namespaces(7)` 手册页里那个绑定挂载遮蔽 `/etc/shadow` 的例子推翻。
- "有语义缺口所以必须进内核"——被 BranchFS 的用户态实现推翻。
- 逐项打勾的对照表——BranchFS 已经在这上面出过问题,一格错整张表都可疑。
